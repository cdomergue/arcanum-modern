Offline authoring guide

Build a place in Arcanum

Edit a zone, furnish a house, write a conversation or prepare a campaign. Work in a project folder, try the result in a separate game copy, then choose the export that fits your content.

This guide works offline and includes Windows and Linux build instructions. Menu labels are in English; names taken from the game keep the installation's language.

1. Install and open a project

You need your own Arcanum installation. WorldED reads its graphics, prototypes, scripts and maps. The editor ZIP contains tools and libraries, but no game archives or saves.

  1. Extract the whole worlded-renaissance-win.zip into a folder such as D:\Tools\WorldED.
  2. Run worlded-explorer.exe. Keep the DLLs, plugin folders and worlded-native-inventory.exe beside it. Install the x64 Microsoft C++ runtime if Windows reports it missing.
  3. Select the game folder containing the DAT archives and modules, not a folder containing only the executable. WorldED remembers the last installation it opened successfully.
  4. Open the world view, select a sector and save it into a separate project folder, such as D:\WorldEDProjects\riverside-house.

Use File > Installation > Open installation… to choose another game. File > Change project installation… changes a project's association when the installation moves.

worlded-explorer.exe --game "D:/Games/Arcanum" --world
worlded-explorer.exe --game "D:/Games/Arcanum" --world-sector 1200,1150
worlded-explorer.exe --project "D:/WorldEDProjects/riverside-house"
Keep the installation used as your authoring reference unchanged. Replacing its resources while editing can invalidate comparisons and update exports.

2. Find your way around

The library is on the left, the scene in the middle, and selection properties, campaign context and neighboring sectors on the right. The toolbar's Mode selector controls what the mouse edits.

ModeUse it for
ObjectsSelect, move, copy and configure objects; Shift-drag ground items into project inventories.
GroundSelect or paint cells, sample materials and copy floor sections.
RoofsEdit the larger roof cells at roof height.
CharactersPlace and configure project NPCs; inspect campaign characters.
ScriptsInspect object, tile and sector attachments.
BlockingInspect collision sources and toggle manual blocked cells.

File manages projects and exports; Edit contains history and selection commands; Zone contains environment, lights and references. Resources opens scripts, dialogues and campaigns. View controls framing and visibility. Test prepares playable copies.

Campaign context and project objects

The campaign overlay shows initial map content, including NPC positions. It does not show a particular save's occupants. Context objects are read-only; project objects can be edited. To change an existing mobile object deliberately, use Zone > Import campaign object for update…. This retains its GUID. Ordinary duplication creates a different identity. The update review still checks whether the intended change can be applied to an existing save.

Open a sector beside the active zone to study or copy a structure. Copied construction objects receive new identities; quest scripts and chest contents are cleared. Inspect the copies before exporting. Each open zone has its own unsaved changes and history.

3. Build your first zone

Start with a small furnished room: one door, one chest and a clear approach from outside. Choose open ground with enough room for the roof. A saleable house must fit inside one sector of Arcanum's main map.

  1. Open the sector and save a project outside the game installation.
  2. In Objects mode, remove scenery occupying the site. Leave a route to the entrance.
  3. In Ground mode, paint a small rectangle of indoor floor.
  4. Drag matching walls and a door from the object library. Match their orientation. Leave the doorway free of wall pieces and furniture.
  5. Add a chest, bed and furniture. Double-click each object to inspect its properties and use pixel offsets for fine placement.
  6. Add roof pieces, then hide roofs to inspect the room underneath.
  7. Check Blocking, save the project and create a test copy. Walk through the entrance in both directions with the whole party.
A door can look clear while its collision still blocks passage. Include a companion that cannot jump through windows in your test. The editor preview is not a pathfinding simulation.

4. Ground, roofs and facades

In Ground or Roofs mode, drag a rectangle to select cells. Choose a material under Ground / Roofs and use Apply to selection, or enable Paint and drag a brush. A completed stroke is one undo step. Escape cancels a stroke. Right-click a cell and choose Sample this cell to locate its material.

Automatic transitions use the installation's outdoor tile rules, including shores and water depths. Exact tiles preserve the selected piece. A stroke is refused if graphics are missing, materials cannot connect or a transition would cross the sector boundary. Edit the neighboring sector separately.

A sector has 64 × 64 ground cells. Each roof piece covers 4 × 4 ground cells, so the roof grid is 16 × 16. Use Show roofs to change their visibility while editing. Check the game's roof occlusion after exporting.

Place a facade or rug

  1. Open the Facades library and search for an assembly.
  2. Choose its supplied orientation; flipped variants are separate entries.
  3. Click Place facade or double-click the preview, then click the destination.

WorldED places the native footprint, frame order and walkability together. Empty footprint cells retain their ground. The complete assembly must fit inside the active sector. Escape cancels; Undo removes the placement as one edit. Sampling one existing facade cell selects an exact piece, not the complete assembly.

Read the blocking overlay

Bright red hatching marks manual blocking; left-click to toggle it. Dark red indicates terrain or object blocking. Removing a manual blocker will not remove a wall's collision. Inspect the material and object on the cell as well.

5. Objects and inventories

Drag to move, Ctrl+D to duplicate and Delete to remove a selection. Double-click an object to configure its position, appearance, properties and script events. Changes stay in memory until you save.

Select one project character or container, then choose Edit > Inventory…. Add items, set quantities and choose backpack cells or supported equipment slots. Arrange backpack finds non-overlapping storage positions. Containers cannot equip items.

The native storage grid is ten columns wide, with twelve rows for characters and ninety-six for containers. Equipment uses separate slots. The editor checks item size and slot conflicts; race, gender, character graphics and other engine restrictions require a game test.

To store a ground item, hold Shift, drag it onto a project character or container, and release the mouse while holding Shift. The item keeps its identity and properties and takes a free backpack position. Select several items first to transfer them together. If any cannot be transferred, the whole operation is refused.

Ctrl+Z returns the item to its original position; Redo stores it again. Escape cancels a drag. The read-only campaign overlay cannot receive items.

Saving a manual inventory disables the owner's random inventory source. Authored contents describe the initial inventory of a new owner. They do not refill a chest that a player has already looted.

Keep owners and inventory MOBs together. The editor maintains their references when copying, moving and deleting owners. An inventory with missing referenced MOBs cannot be edited safely; include those files in the project first.

6. Characters and routines

Drag an NPC or creature from the library, then double-click it or use Configure character…. Configure facing, descriptions, portraits, stats, skills, training, resistances, AI, reaction, faction and scripts. Untouched values remain inherited from the prototype.

Daily routine

Enter day and night positions in world tile coordinates. Day runs from 06:00 to 21:00. Add waypoints in order, then enable Day waypoints or Night waypoints in Behavior. The route repeats. Editing it resets its starting waypoint. Test that every stop is reachable.

Routes can cross sectors on the same map. A destination in sector 0,0 cannot be authored from another sector because its coordinates overlap the local-position encoding.

Spells, technology and generators

College levels range from 0 to 5, technology degrees from 0 to 7, and the mastered college from 0 to 15 or None. Setting these authoring values does not spend character points.

The Generator tab makes an NPC an invisible spawning template. Reserve an unused generator ID from 0 to 255; shared IDs share counters. Set the interval, concurrent population, total limit and active times. A zero alive limit or no active time produces no spawns. Test generator limits in the game.

The Effects tab also applies to scenery. Additive blending suits flames whose black backgrounds should disappear. Foreground and background Eye Candy effects have separate settings.

7. Lights and environment

Zone > Lights… manages independent lights. Set cell, pixel offset, art, color and frame. Directional lights have 32 directions; ordinary lights have eight. Disabled keeps a record without illuminating the scene.

Indoors and Outdoors use the sector lighting schedule. Leave both unchecked for a fixed custom color. Dark light/shadow darkens an area; Animate uses a moving light texture. View > Light preview draws approximate halos, not the engine's final occlusion or shadows.

Zone > Sector properties… sets music, ambient sound, a lighting scheme and the magic/technology adjustment. These affect the whole sector, including land outside a house. Test sound and lighting by day and night.

Housing represents authored lights with persistent invisible objects. Removed independent lights are disabled in place to preserve saved record ordering. Check first entry and save/reload.

8. Scripts and conversations

Script Editor Renaissance edits Arcanum scripts and conversations without opening a map. It runs on Windows and Linux and shares its script editor and compiler with WorldED. New scripts use structured .wscript source. Existing .scr files open as native instructions, with their condition, then action and else action visible on each row.

Start a project

On Windows, extract worlded-renaissance-win.zip and run script-editor.exe from the same folder as worlded-explorer.exe. The archive contains both editors, their shared runtime and this guide. Keep the libraries and plugin folders beside the executables. You can launch the script editor without opening WorldED.

On Linux, build the script-editor target with the instructions below and run it from the build folder. It uses the Qt libraries installed for that build.

Choose File > Open project folder for a folder containing your scripts and dialogues. Choose Arcanum installation adds campaign resources to the library and loads the game's operation descriptions. The installation is remembered. Opening a game resource creates a copy that needs a destination when saved; the editor does not write back into an archive.

Use the library filter to find a filename or resource ID. Double-click to open it in a tab. You can work on several scripts and dialogues together.

In WorldED, Resources > Script editor opens the standalone application. WorldED's own script dialogs use the same editor. Save and close a project before editing its files in the other application; open tabs are not synchronized.

Write a structured script

Choose File > New structured script. Statements end with a semicolon; blocks use braces. For example:

let total = 0;
for (let i = 0; i < 5; i++) {
    if (i == 2) {
        continue;
    }
    total += i;
}
return default;

Press F7 to compile. Errors include a source line and column. The compiled instructions tab lets you inspect the result. Ctrl+Space lists completions.

The language supports if/else, while, for, break, continue, named labels, goto, comparisons, &&, ||, !, addition, subtraction and multiplication. Use // for a comment. Integer values are signed 32-bit numbers; hexadecimal constants use 0x. Division is rejected because the pinned engine implements its division instruction incorrectly.

Native actions and conditions accept their full SAT_… or SCT_… name, or the lowercase suffix. Actions are statements; conditions belong in if and loops. Use structured loops and goto label; for control flow. The compiler manages instruction numbers.

Expression Meaning
let count = 0; Named numeric local
global(1900) Campaign global variable; valid indices 0–1999
flag(3000) Campaign global flag; valid indices 0–3199
counter(0) One of the script's four counters
pc_var(player, 8) Per-character variable with an explicit object focus
pc_flag(self, 2) Per-character flag with an explicit object focus
player, self, attachee, triggerer, current, extra Object context
object(11, 0) Indexed object focus; here, local object zero
raw(type, value) Explicit native operand for experienced authors

Reserve global and flag indices for your project before using them. Example indices in this guide are not allocations. The engine has ten numeric local slots, shared by named variables and expression temporaries. Simplify an expression if compilation runs out of slots. Keep loops short: the runtime limits an invocation to 1,000 executed instructions.

return; skips the default event behavior. return default; allows it. Choose according to the event you attach the script to.

Saving a structured script keeps the .wscript and writes a companion .scr. That companion also holds the script properties. Keep both files together. Use Build project after changing source used by a dialogue so both compiled resources use the same instruction numbers.

Edit a native script

Open a .scr file. Double-click its condition, then action or else action to choose an operation and edit its operands. The picker lists all 53 conditions or 142 actions, with a search field. Operand controls distinguish numbers and variable indices from object focuses. PC variables and flags have a character focus selector.

Add action and Add condition insert after the selected row. Duplicate copies it. Up, Down and Delete change the instruction order. Undo and redo restore native instruction edits. Constant jumps within this script follow their destination when rows move. Deleting a destination still referenced by a jump is rejected; change the jump first.

Review computed jumps, incoming calls from other scripts and numeric dialogue targets after inserting, deleting or moving rows. Those references cannot all be resolved from the current document. Unknown opcodes, unknown operand types and unused binary fields are retained. A native file is not converted into structured source on opening.

Script > Properties edits the description, four counters, 32 local flags and trap, speech, radius and teleport flags. The description must fit 39 Windows-1252 bytes when changed. Local flags and behavior flags are separate fields. Untouched unknown bits remain intact.

Write a conversation

Choose File > New dialogue, or open a .dlg or .wdlg. The table contains the native seven fields: line ID, text, alternate text, intelligence requirement, condition, destination and effect. Use the editor's validation and preview to check the conversation. Preview follows text and links; it does not execute conditions or effects. These fields use Arcanum's native dialogue syntax.

Give the dialogue and its companion script the same filename stem. For example, 01999.wdlg and 01999.wscript belong together. Open companion finds the matching file in the same folder or a WorldED project's source/export folders.

A positive destination selects another dialogue line; zero ends the conversation. A negative destination resumes a numbered script instruction. To keep that last kind of destination stable while editing structured source, use a named label:

dialog(1);
label reward:
global(1900) = 1;
return;

Set the dialogue response's Target to @reward. Build the project to resolve it into the native negative instruction number. Labels are case-sensitive. A missing label stops compilation. A label at instruction zero cannot be used: zero means “end conversation” in a DLG. Put an initial instruction before the entry point, as in this example.

Save named destinations in .wdlg source. Exported .dlg files contain numbers; keep the source for later edits. When saving a native dialogue containing a named destination, the editor asks for a .wdlg destination so the label is retained. Text must fit Windows-1252. The game supports at most five player responses at a time.

Build and use the resources

Save all open documents, then choose Script > Build project. Select a new or empty export folder outside the source project. The editor compiles structured scripts, resolves dialogue labels and retains native-only scripts and dialogues. It writes scr/ and dlg/ directories. Duplicate source names or duplicate native resources stop the build. A source file takes precedence over its compiled companion. Building never overwrites a populated export folder.

For one document, Export compiled file writes a .scr or .dlg at a chosen path. Exporting one script does not rebuild a linked dialogue. Prefer a project build when they share named destinations.

WorldED stores structured scripts and dialogue sources in script-sources/, and compiled resources in exports/scr/ and exports/dlg/. Applying a structured script in WorldED also recompiles a matching project .wdlg when present. The files can be included in housing and campaign-update exports. Attach the script to the intended object or event; a resource file alone does not attach itself.

Test in a separate game copy. Check the event, conversation branches and effects in the game, including repeat visits and a saved game. Compilation checks data and references; it cannot establish that a quest behaves as intended.

Example: an unlocked chest that awards 50 coins once

This script belongs on SAP_USE of a new, unlocked container. It awards the player 50 coins on first use, remembers that reward in counter 0, and allows the normal container interaction. Each attachment has its own counter; two chests using this script can each award one payment.

if (counter(0) == 0) {
    counter(0) = 1;
    adjust_gold(player, 50);
}
return default;

The complete source is 49000_reward_chest.wscript. Choose an unused ID before adding it to your mod; 49000 is an example, not a reserved allocation.

In WorldED, select the chest, create the script through Resources > New script…, paste the source, and Validate. Enable Attach to selected object on apply, choose SAP_USE, then apply and save the zone. Check that counter 0 is initially zero on the attachment. Use Load defaults from SCR only when you intend to reset its initial flags and counters.

In a disposable game copy, note the player's gold and open the chest. Expect 50 more coins and an open inventory. Open it again: gold must stay unchanged. Save, leave the area, return and reload; the reward must still be consumed. Restoring a copy of a save from before first use lets you repeat that test.

return default; matters here. Replacing it with return; suppresses the normal container interaction. An attachment on SAP_EXAMINE would run on examining the chest rather than using it. Neither recompiling nor replacing the SCR resets the counter already recorded in a saved game.

The same chest in the native editor

Choose File > New native script in Script Editor. Press Add action four times so rows 0 through 3 exist before entering their jump targets. Double-click each cell to enter the following operations. Search by the enum name if your installation displays a translated description.

Row Condition Then action Else action
0 SCT_EQ: Counter 0 equals Number 0 SAT_GOTO: Number 1 SAT_GOTO: Number 3
1 SCT_TRUE SAT_ASSIGN_NUM: Counter 0 = Number 1 SAT_DO_NOTHING
2 SCT_TRUE SAT_ADJUST_GOLD: Player, Number 50 SAT_DO_NOTHING
3 SCT_TRUE SAT_RETURN_AND_RUN_DEFAULT SAT_DO_NOTHING

For a Counter operand, enter its index, 0, in the adjacent value field. For a Number operand, enter the literal value. On row 2, choose Player as the object focus; its index value can remain zero. Leave all four counters at zero in Properties. Row numbers in this table are zero-based, as in the editor's Line column.

On first use, row 0 selects row 1, which marks the reward consumed; row 2 grants the coins. On subsequent uses, row 0 jumps directly to row 3. Both paths allow the normal chest behavior. This is the same behavior as the structured example, although the compiler may generate a different number of instructions.

Validate and save as an unused numeric resource name, for example 49002_native_reward_chest.scr. To add it to a WorldED scene, save and close the scene first, place the SCR in its exports/scr/ folder, then reopen the scene. Find it in Resources > Scripts & dialogues…, attach it to the chest's SAP_USE event and save. Use this native script or the structured chest script on that event; they are two ways to implement the same behavior.

reward_chest.native.txt contains the native listing for comparison. It is a reference for the table above, not .wscript source. The native listing tab is read-only; edit through the instruction cells.

Example: a payment offered in a conversation

Create a project NPC and attach this script to SAP_DIALOG:

dialog(1);
return;

label reward:
if (counter(0) == 0) {
    counter(0) = 1;
    adjust_gold(player, 50);
}
return;

Create a matching dialogue with these three rows. Leave conditions and effects blank. On the NPC line, the alternate text may repeat the same sentence.

ID Speaker Text Intelligence Target
1 NPC I have fifty coins set aside for you. Blank 0
2 Player response I will collect them now. 1 @reward
3 Player response I will come back later. 1 0

The supplied 49001_reward_keeper.wscript and 49001_reward_keeper.wdlg contain this example. Copy both into a working folder and use Open project folder, then Build project. Use the same filename stem for both if you rename them. The native output is a SCR/DLG pair; keep the WScript/WDlg sources.

In WorldED, apply the script and dialogue under the same resource name, attach the script to the NPC's SAP_DIALOG event and save the scene. If importing the supplied pair into a saved scene, close it first, put the source files under script-sources/, and copy the compiled SCR and DLG into exports/scr/ and exports/dlg/. Reopen the scene before attaching or exporting them.

The first two compiled instructions are the dialogue call and the return, so reward resolves to instruction 2 in this example. The exported response target is therefore -2. A native-only conversation can use -2 directly when its companion SCR has that entry point, but you must update the number if rows move. Keeping @reward in .wdlg source lets a project build recalculate it.

Test “come back later” first: the conversation should close without a payment. Talk again and collect it: gold should rise by 50. Talk and collect a second time, then save/reload and repeat: no further payment should be granted. The response remains visible in this example; the counter prevents repeat rewards. There is no quest-completion check in this script. Add the intended native quest condition before using it as a real quest reward.

Command line and builds

The command-line compiler uses the same code as the editors and needs no display server. On Windows use script-editor.exe in these commands:

./script-editor --compile 01999.wscript --output 01999.scr
./script-editor --compile-project ./my-project --output ./compiled-project
./script-editor --validate 01999.scr

Single-file compilation creates default script properties. A project build reads properties from the source's companion SCR, or exports/scr/ in a WorldED project. Validation reports unknown operations and references that need review. Keep the source files and properties under version control together.

Follow Building WorldED to configure Qt, zlib and CMake on Windows or Linux. The same CMake project provides script-editor and script-editor-check; the standalone editor needs no engine build or map.

cmake --build build/worlded-linux --target script-editor script-editor-check
ctest --test-dir build/worlded-linux -R script_editor --output-on-failure

On Windows add --config Release to the build and -C Release to CTest. The script editor and its guide are included in worlded-renaissance-win.zip. Follow the Windows packaging steps in Building WorldED to produce that shared archive. The packager checks executable startup and the Qt platform plugin without the SDK on PATH.

9. Test in the game

Save the project and choose Test in a copy…. Select a named save, a compatible Renaissance executable, language and new output folder outside the installation. Allow disk space for another game copy. Configure a marker through Map location if needed.

WorldED copies the selected save and resources, exports the scene and moves the party to the sector. The executable must support --worlded-test; original game executables and shell launchers are refused.

A full-sector zone test requires a save that has never loaded that sector. It cannot merge saved DIF changes with a replacement SEC. Test additive housing and world-update packages separately on copies of already visited saves.

NPC inventory generation uses the native helper beside WorldED and runs inside the copy. It does not generate project-export contents. Read test-launch.log and inventory-generation.log for failures. Resume test uses the copy's playtest.json; later project edits need a new copy.

  • Cross entrances in both directions with companions.
  • Use doors, chests, beds, scripts and conversations.
  • Move items, save, travel away, return and reload.
  • Inspect lighting, roof behavior and vegetation shadows.
  • For persistent updates, test both first discovery and a previously visited sector.

10. Create a mod for Arcanum Renaissance

A mod needs authored content, an installation method and a test that exercises what the player will do. Start with a small change that you can recognize in the game. This walkthrough adds an unlocked chest that awards 50 coins on its first use, then remains an ordinary storage chest.

You need an Arcanum installation, a Renaissance executable compatible with world updates, WorldED, and Python 3 for the package installer. The Windows editor ZIP contains WorldED, Script Editor, the installer and the example sources.

Choose the export before building the mod

What you want to distribute Project and export Existing saves
New objects and supported changes to an existing zone Scene project; Export Renaissance update package… Applies supported operations to visited and unvisited sectors; conflicts are reported
A property sold by the estate agent House scene, housing export and catalogue entry Uses housing ownership and installation rules; follow the housing sections
Campaign settings, maps or replacements of shared resources Resources > Campaign…, then Export overrides… Test in an independent installation with a new game; replacement files do not migrate visited sectors or quest state

The chest walkthrough uses a Renaissance update package. Existing NPC statistics, inventories, schedules and script attachments are outside that exporter's supported changes. A new container can carry its initial inventory and script attachment. If the export review reports an unsupported edit, resolve it before distributing the mod. A raw sector export is not a substitute for a save-compatible update.

1. Create the source project

Open the target installation in WorldED, choose a sector where the player can reach the chest, and save the scene outside the installation. For example:

D:/Mods/reward-chest/
    source/       WorldED scene project
    exports/      Versioned packages ready for installation
    tests/        Disposable game copies

The scene captures the original sector as its reference. Keep reference.bin and selections.bin with building.json and the rest of the project. For an older project without a reference, use Zone > Update reference… with the installation from which it was created. Do not adopt a different release just to dismiss a mismatch.

2. Add the chest and its behavior

Place a new container from the palette. Use an unlocked prototype or clear the lock in its properties. Put it on a reachable cell and keep its approach clear. An empty chest makes the first test easier to read.

Select the chest and choose Resources > New script…. Pick an unused numeric ID and a name such as reward_chest. Check the script library and any installed mods before reserving an ID; 49000 in the example is not guaranteed to be free.

Paste the complete reward-chest example from the scripts section, then Validate. Enable Attach to selected object on apply, choose SAP_USE, and apply the script to the project. Check that the attachment's counter 0 starts at zero. Save the scene. Creating a script file by itself does not attach it to the chest.

If you work in Script Editor separately, save the WorldED scene first, edit its matching source under script-sources/, then reopen the scene and apply the script in WorldED. Do not edit the same project simultaneously in both windows. The scene's compiled resources must reflect the source before export.

3. Try the scene in a disposable copy

Use Test in a copy…, with a named save that has never loaded this sector, the Renaissance executable, and a new output folder outside the installation. This checks the scene as a whole. It does not exercise installation of the final update package into an already visited sector.

Record the player's gold, use the chest, and check that it opens and gold rises by 50. Close and use it again: gold must not rise again. Put an item inside, save, leave the area, return and reload. The item should remain and the reward should stay consumed. Also check that companions can reach the chest.

For a fresh first-use test, restore a disposable save from before the first use. Recompiling a script does not reset a counter already stored in a save.

4. Export the installable package

Choose File > Export Renaissance update package…. Set a stable package ID, for example myname.reward-chest, and display version 1.0.0. The first revision is 1. Use your own namespace so the ID does not collide with another author's mod.

Read the review. For this example it should include the new chest and its new script resource, without changes to unrelated campaign objects. Export into a new folder such as D:/Mods/reward-chest/exports/revision-1. WorldED writes the package and saves its publication history in the source project.

The package contains manifest.json, runtime.rwp and the resources it needs. Keep the entire folder. Do not hand-edit a published revision or remove files because they look unused. Exporting does not install the mod.

5. Test installation of the actual package

Prepare a separate copy of the game and a copy of a named save, including all files belonging to that slot. Close that copy before installing. Run these commands from the extracted WorldED folder:

python tools/world-updates/package.py check "D:/Mods/reward-chest/exports/revision-1"
python tools/world-updates/package.py install "D:/Mods/reward-chest/exports/revision-1" "D:/ArcanumTests/reward-chest"

On Linux use python3 and the corresponding paths. Start Renaissance in the test installation and load the copied save. Repeat the chest test with a save that has already visited the sector, then with one that has never visited it. Save and reload, including after putting an item in the chest. The package must not add a second chest or refill an existing one.

The installer registers the revision under ArcanumModern/world-updates/<package-id>/<revision>. The engine applies pending operations when their sector loads. If an expected old value differs, it records a conflict instead of overwriting the player's state. Check the module's Save/WorldUpdates/updates.log when an operation does not appear. The engine also makes a pre-update backup there; keep your independent test backups.

6. Give players a complete download

Zip the exported package folder with a short README. Include the mod name and version, required Renaissance version, dependencies, installation commands and whether a new game is needed. State that players must close the game before installation and keep a backup of the complete save slot.

For this package workflow, direct players to extract the mod and run the same check and install commands against their own installation. They need Python 3 and tools/world-updates/package.py from the editor ZIP. Do not tell them to copy manifest.json into the game root or overwrite a SEC file.

Distribute your exported resources, README and any assets you have permission to share. Keep game archives, personal saves, test installations, cache files and machine-specific settings out of the download. If you share editable sources, provide them separately with their .wscript and .wdlg files. They are useful to authors but are not loaded by the game.

Maintain and remove a mod

Keep the scene's world-update.json and original reference. Reopen that same project to publish a later revision under the same package ID. The exporter retains previous operations and adds supported changes, so players can skip an intermediate release.

Published scripts and dialogues are immutable resources in this update format. A changed script needs a new resource ID and a supported way to attach it; replacing an existing object's script attachment is not supported by this exporter. Plan those changes explicitly rather than overwriting old SCR files.

Removing the package folder does not undo changes already saved in the world. A save that depends on a missing package may refuse to load. To roll back a test, restore the complete earlier save slot together with the registry and resource versions it used. For a distributed mod, document this limitation in the README; do not advertise deletion of its files as a clean uninstall.

11. Create a saleable house

A housing property belongs to one sector of arcanum1-024-fixed, the main map. One property per sector is supported. Separate interior maps and multi-sector houses are outside this workflow.

Build with fresh project objects. Housing must not take over existing campaign GUIDs. To replace baseline scenery, remove the original and place a new instance. Check the entrance, roof and storage before exporting.

Clear vegetation

Deleting baseline scenery records its removal. For cells that must also be clear of vegetation variants, create vegetation.mes in the project root:

{1300}{62}
{1301}{62}

The key is localY * 64 + localX; these entries address (20,20) and (21,20). Mask 30 clears trees, 32 clears plants, and 62 clears both. Clearance also hides authored vegetation on those cells. Keep it away from plants you want to retain.

Export the saved scene

Run this from the extracted editor folder in PowerShell, choosing a destination that does not exist:

.\worlded-house-export.exe "D:/Games/Arcanum" `
  "D:/WorldEDProjects/riverside-house" "D:/WorldEDExports/riverside-house"

On Linux, use worlded-house-export with the same arguments. The exporter reads the sector from building.json and compares it against the installation used as the reference.

A guard is optional. Append --guard GUID for an NPC that should offer estate dialogue. Obtain its persistent 36-character ID beginning with 0200 from the object or worlded decode FILE.mob. A prototype number is not an instance GUID. Repeat the option for several guards. The estate service controls guard dialogue and bed-use events; use other objects or events for custom behavior.

The output includes MOBs, scene roles, surface differences, removal records, optional environment/script/light data, resources and update-template.json. Copy the entire export to a scene folder such as resources/house/riverside_house in the repository. Do not install a raw project SEC over the campaign sector instead of using the housing pack.

Maintain a published property

Keep its complete previous export. For a revision, pass --previous-update /path/to/previous-export. The exporter retains published operations and resources and appends supported changes. Surface corrections expect the last published value. Changing a published MOB or removing an added object requires an explicit migration and is rejected by this exporter.

The housing service handles purchases, keys, ownership, discovery, guard dialogue and beds. World updates handle installation, terrain, roofs, blockers and scenery suppression. Environment settings, sector scripts and independent-light removal use housing metadata hooks. Initial manual contents belong to a new owner; they do not replenish a player's existing storage.

13. Edit a campaign

Resources > Campaign… opens a separate project type with campaign.json, original hashes and resource overrides. Use it for map definitions, travel terrain, connections, shared tables and townmaps.

Edit a selected resource, apply it and save outside the installation. Undo and Redo cover applied edits. Reopening checks original resource hashes. Create test copy produces an independent installation with your overrides and excludes personal saves. Start a new game there.

Maps and travel

New map creates properties, terrain, jump and start-location files and appends a map-list entry. Choose dimensions in sectors and an installed biome. Connect it before trying to enter. Campaign settings edit the adventure name and ID, starting year and hour.

Each terrain.tdf cell represents an entire sector. Filling changes biome codes; stored SECs still override generated terrain. Resizing preserves overlap and updates dimensions, but does not move objects, jumps or artwork. Code-image PNGs store the terrain code's high byte in red and low byte in green, with blue zero. Do not resize, color-correct or convert them to JPEG.

Travel blocking comes from a biome's /b flag. Code 65535 means no terrain and is blocked. This differs from zone-level manual blockers.

Jump points use absolute tile coordinates and one-based destination map IDs: map-list record 5000 is map 1. Add return jumps yourself when needed. ID validation does not prove that landing cells are walkable.

Quests, areas and encounters

Quests / areas / encounters edits structured records. Quests use IDs 1000–1999, with normal, bad-reaction and low-intelligence dialogue entry points for each state and both journal variants. Scripts still control progression.

Areas retain stable positional indices. Encounter groups have weighted entries and NPC prototype/count groups; regional settings control frequency, power and table overrides. Test actual travel routes because a valid definition does not guarantee an encounter will be selected.

Other MES tables keep native syntax. The editor requires unique unsigned IDs and Windows-1252 text without braces. Editing a table rewrites its records, removing comments outside records. Untouched files remain unchanged.

Townmaps and lighting schedules

Townmaps > Create and assign a townmap reserves an ID, folder, campaign map and sector rectangle. Generate artwork with the native helper or import images, then inspect the assignments. Lighting schedules have hourly outdoor and indoor RGB channels. Specify hours 0 and 23; a blank interior row uses interpolation.

Export overrides writes replacement resources for an independent installation. It does not migrate existing quests or visited sectors. Use a world-update package when its supported operations match the change.

14. Update existing saves

A world-update package describes individual guarded changes. It can move a mobile chest without replacing its contents, clear a blocked cell, add scenery or hide original scenery. The project retains an original reference and published operation history.

  1. Open the target sector from the installation you support and save a project. A project without a captured reference needs Zone > Update reference against its original installation.
  2. Make the change. For an existing mobile chest, use Zone > Import campaign object for update to keep its GUID.
  3. Choose File > Export Renaissance update package. Supply a stable lowercase package ID, display version and dependencies, if any.
  4. Read the review. Unsupported changes disable export. Check targets and expected old/new values before choosing a new package folder.
  5. Save the project after export to keep its publication history.

Keep reference.bin, selections.bin and world-update.json. Later exports retain previous operation IDs and resource bytes, then append operations. Do not edit published operations or reuse an ID for another project.

Supported changes

ABI 1 supports ground, roof and blocking cells, new objects, scenery suppression, allowlisted scalar fields and flags, and GUID container/scenery movement within one sector. Static record ordering stays fixed. Static and cross-sector movement are refused.

Existing inventory lists, actor statistics and schedules, existing script attachments, independent lights, sector environment and worldmap labels are not general ABI-1 operations. Importing an owner does not make inventory edits applicable to an existing save. Campaign resource replacement and quest-definition MES merging are separate workflows.

Hand-authored conditional migrations can convert global variables, flags or local-player quest states after saved state loads. They preserve completed/botched outcomes and do not award XP or replay alignment and reaction effects. The contract is documented in tools/world-updates/FORMAT.md.

Install, inspect and recover

Close the game. From the repository or extracted editor package:

python tools/world-updates/package.py check "D:/MyMod/town-update-r1"
python tools/world-updates/package.py install "D:/MyMod/town-update-r1" "D:/TestGames/Arcanum"

Restart the game to load the registry. Bundled packages use bundled.mes; manual installations use index.mes and pin their revision over the bundled default.

Before pending changes apply, the engine backs up the selected save and package resources under the module's Save/WorldUpdates. Unvisited sectors remain pending. A mismatched value or missing target produces a conflict and preserves divergent player state. Applied additions are recorded, so consuming or destroying an object does not respawn it on reload.

Read Save/WorldUpdates/updates.log for outcomes. Missing required packages, downgrades or altered published bytes can refuse loading. Rollback requires the complete earlier save and its matching resources and registry. Removing a package alone cannot undo saved changes.

16. Build on Windows

Run commands from arcanum-modern-source. Install Git, CMake 3.21+, Python 3, Visual Studio C++ Build Tools with a Windows SDK, x64 MSVC Qt 6.4+ and zlib. GUI builds use Qt Widgets, Concurrent and Test. Synthetic tests need no game files.

This PowerShell example uses Visual Studio 2019 and Qt 6.5.3. Match the generator and paths to your installed kit. Do not mix MSVC and MinGW libraries.

$qt = 'C:/Qt/6.5.3/msvc2019_64'
$zlibInstall = Join-Path $PWD 'build/worlded-zlib-install'
git clone --depth 1 --branch v1.3.2 https://github.com/madler/zlib.git build/worlded-zlib-src
cmake -S build/worlded-zlib-src -B build/worlded-zlib `
  -G 'Visual Studio 16 2019' -A x64 `
  -DZLIB_BUILD_SHARED=OFF -DZLIB_BUILD_TESTING=OFF `
  "-DCMAKE_INSTALL_PREFIX=$zlibInstall"
cmake --build build/worlded-zlib --config Release --parallel
cmake --install build/worlded-zlib --config Release

cmake -S tools/worlded -B build/worlded-windows `
  -G 'Visual Studio 16 2019' -A x64 -DWORLDED_BUILD_GUI=ON `
  "-DCMAKE_PREFIX_PATH=$qt" `
  "-DZLIB_INCLUDE_DIR=$zlibInstall/include" `
  "-DZLIB_LIBRARY=$zlibInstall/lib/zs.lib"
cmake --build build/worlded-windows --config Release --parallel
$env:PATH = "$qt/bin;$env:PATH"
$env:PYTHONUTF8 = '1'
ctest --test-dir build/worlded-windows -C Release --output-on-failure

Release contains worlded-explorer.exe, worlded.exe, worlded-house-export.exe and script-editor.exe. Set Python3_EXECUTABLE during configuration if CMake finds the wrong interpreter. Other zlib packages may use a different library filename.

Native inventory helper

The helper belongs to the Renaissance engine build. Prepare and configure that engine using docs/development.md, then build:

cmake --build build/engine --config Release --target worlded-native-inventory

Replace build/engine with your engine build directory. Copy the helper and its matching avformat-*.dll, avcodec-*.dll and avutil-*.dll beside the editor. The release workflow does this automatically.

Build the helper with the engine target as on Windows. For an existing Linux Ninja engine build, you can also use:

python3 tools/worlded/build_engine_check.py --build-dir build --inventory

For the format CLI alone, set -DWORLDED_BUILD_GUI=OFF. It still needs zlib and C++17, but does not build the GUI or housing exporter.

18. Package a Windows release

The Release packages workflow builds and tests WorldED on Windows, includes the matching engine's native helper and produces worlded-renaissance-win.zip. The release job waits for it and includes its checksum in SHA256SUMS.txt.

The archive opens directly into an editor folder with executables, DLLs, plugins, this tutorial, reference documentation and the update installer. To create it locally after building WorldED and the helper:

python tools/package-worlded-windows.py `
  --build-dir build/worlded-windows `
  --inventory-helper build/engine/Release/worlded-native-inventory.exe `
  --qt-bin "$qt/bin" --smoke-test

The helper's DLLs must be beside it. Use --engine-package dist/ArcanumModern-windows-x64.zip to take them and FFmpeg notices from a matching game package. If zlib is dynamic, pass --extra-dll path/to/zlib1.dll. Output defaults to dist/worlded-renaissance-win.zip.

The packager runs windeployqt, verifies required files and hashes, and can launch all five programs and check the script editor platform plugin after extraction with the Qt SDK removed from PATH. To check an archive:

python tools/package-worlded-windows.py --verify dist/worlded-renaissance-win.zip --smoke-test

A tag beginning with v triggers the release workflow. It creates or updates a draft and refuses to overwrite a published release. Manual runs produce artifacts without creating a release. Commit before tagging so binaries and tutorial come from the same revision.

20. Troubleshooting

The editor cannot find the game

Select the installation with DAT archives and modules. Update a moved installation through File > Installation. Keep the project outside that folder. An unavailable remembered drive is not a damaged project.

Windows reports a missing DLL or Qt plugin

Extract the complete ZIP and keep platforms/qwindows.dll and the Qt DLLs with it. CMake copies the required Qt DLLs and platform plugins beside Windows build-tree executables. Packaged builds must pass the smoke test without the Qt SDK on PATH. Install the x64 Microsoft C++ runtime if Windows names it as missing.

A test cannot generate inventories

Check for the native helper and matching FFmpeg DLLs beside the editor. Read inventory-generation.log. The helper must match the Renaissance engine build.

The save already visited the sector

Choose an unvisited save for a full-sector test. Use a supported additive package on a copied save for an existing world. Do not delete original DIF data to force the test.

An open door blocks the party

Inspect manual blocking, terrain walkability, wall pieces, portal orientation and overlapping objects. Test both directions with a companion that cannot use windows.

A rug is missing or fragmented

Place the complete assembly from Facades. Check its sector bounds and installation graphics. Sampling a cell selects only an exact piece.

Shift-dropping an item has no effect

Use Objects mode and a ground item in the project. Keep Shift held when releasing over a project character or container. Read the status bar: an invalid target, missing reference, conflicting stack or full inventory refuses the transfer. Campaign context remains read-only.

The seller does not list the house

Check the catalogue, slot, exported sector and scene folder; rebuild the pack. Verify the catalogue path, language folders and top-level package registration. Restart the matching engine before testing.

An update is refused or conflicts

Read the export review and Save/WorldUpdates/updates.log. Check the original reference, dependencies and immutable history. Rollback restores a complete earlier save and matching resources; uninstalling alone is insufficient.

Linux cannot load Qt or ICU

Install the runtime dependencies of the chosen Qt kit. Check its version and use a fresh build directory when switching kits. Recompiling does not supply a missing runtime library.
